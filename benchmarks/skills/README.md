# Поведенческие проверки рабочих скилов

`cases.json` содержит 12 небольших задач для девяти новых skills.
`fixtures/` — исходные примеры, `rubric.json` — критерии только для оценщика.
Набор включает корректный код, код с дефектами, миграцию, архитектуру, тексты
и векторные ассеты. Он дополняет unit tests, не доказывает общую эффективность.

## Подготовка без обращения к модели

```bash
python3 benchmarks/skills/prepare_cases.py \
  --model gpt-5.6-luna --output /tmp/skills-luna-run-01
```

Для Terra выбери `--model gpt-5.6-terra`; для одной задачи добавь, например,
`--case database-migration`. Команда не запускает модель (`model_requests: 0`).
Она создаёт независимые каталоги с собранным skill, выбранными профилями,
входами, `prompt.md` и пустым `output/`. Повторное использование каталога
запрещено. Manifest фиксирует модель и SHA-256 skill, inputs, prompt.

## Запуск и оценка

Передавай только один `prompt.md` и его каталог новому worker с явно выбранной
Luna/Terra. Применяй доступный в среде механизм запуска модели; этот репозиторий
не предполагает несуществующий CLI или API key. Запуск модели требует разрешений
и доступности модели в текущей среде. Не передавай rubric, свои подозрения,
ожидаемый ответ или результаты предыдущего worker. Ограничь workspace одним
case directory, если runtime это позволяет: текстовый запрет не является sandbox.

Оценщик читает rubric после результата и отмечает каждый критерий как
passed/failed/not-verified с доказательством. Отдельно учитывай найденные
дефекты, ложные findings на clean cases, сохранение scope и реально выполненные
проверки. Не считай упоминание ключевого слова успешным выполнением.

Для database-migration проверь SQLite-данные и старый INSERT; для icon/logo
проверь SVG и отрендеренный preview с фактическими размерами элементов.
XML parsing не доказывает визуальное качество. Для content/UX сравни факты с
брифом и измерь ограничения длины. Без нужного инструмента используй
not-verified, не автоматический passed.

Сохраняй output и протокол модели локально вне Git. В отчёте фиксируй точный
model id, effort (если известен), snapshot/hash и ограничения среды. Для
сравнения моделей нужны одинаковые inputs, capabilities и несколько повторов
в новых контекстах. Первый smoke ниже не является таким сравнением.

Результаты первой проверки: [initial-smoke.md](initial-smoke.md).

## Основания правил

Правила написаны для этого проекта; большие внешние инструкции не копировались.
При проектировании использованы [Google: review comments](https://google.github.io/eng-practices/review/reviewer/comments.html)
для объяснения причин замечаний, [WAI-ARIA APG](https://www.w3.org/WAI/ARIA/apg/patterns/dialog-modal/)
для поведения modal dialog и [C4](https://c4model.com/diagrams) для выбора уровня
архитектурной схемы. В database profiles сохранены ссылки на документацию
PostgreSQL, MySQL и SQLite. Версионные правила нужно сверять с целевым проектом.
Шкала приоритетов, упаковка, автономность и протокол оценки — решения этого репозитория.
